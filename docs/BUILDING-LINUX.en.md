# Building Azki Simulator on Linux

[简体中文](BUILDING-LINUX.md) · [Home](../README.en.md) · [macOS build notes](BUILDING.en.md)

## Status

Linux support is currently **development/CI grade**: build the engine from source, run firmware headless, and drive it through the local control surface. There are no `.deb`/Flatpak packages and no cross-distribution promises; Arch Linux (Wayland) is the reference environment, and other distributions map the same dependency list onto their package managers. Real-phone Bluetooth radio pairing (BlueZ) is not implemented yet. The platform branches of the virtual peer protocol layer (quick-app and watchface installation and so on) are ported — AES/ECDH through libcrypto, peer credentials through `SO_PEERCRED`. The peer's **own half** now has an end-to-end test (`tests/test_virtual_peer_session.py`): the unix socket session, the kernel peer-credential gate, the SMP Just Works dialogue (with the confirm value computed by an independent implementation), the CCM/MIC link layer, and the staging of a synthetic package with its receipt — all of it runs on both hosts. The **guest half** (HCI/L2CAP/ATT, the business channel, delivering a package to a device) is still unverified end to end and counts as verified only once a real package has been imported and pushed through. One divergence in the peer's own code turned up on the way: the `VirtualAir` class in `virtual_peer/smp.py` documents "two independent endpoint keys", but one crossing seals with one key and opens with the other, so it only holds when both endpoints derive the same key — which is the case for the legacy pairing flow, where the temporary key is the link key. A test pins that difference; think it through before changing it.

## Requirements

- Linux on x86_64 or aarch64. The build host is the run host.
- Build dependencies (Arch package names): `base-devel meson ninja pkgconf python glib2 pixman zlib libffi pcre2 zstd dtc libcap openssl`.
- Runtime: `bubblewrap` (process isolation, requires unprivileged user namespaces) and `ffmpeg` (optional, screen recording).
- Desktop app build dependency: `dotnet-sdk` (.NET SDK, builds the Avalonia app under `linux/`).
- The first build downloads upstream sources for QEMU, CPython and the Python wheels.

On Debian/Ubuntu the equivalent packages are: `build-essential meson ninja-build pkg-config python3 libglib2.0-dev libpixman-1-dev zlib1g-dev libffi-dev libpcre2-dev libzstd-dev device-tree-compiler libcap-dev libssl-dev bubblewrap`.

## Building

```sh
git clone git@github.com:AzumaChiaki/Azki-Simulator.git
cd Azki-Simulator
./scripts/build.sh debug
```

On Linux `build.sh` dispatches to `scripts/build-linux.sh`: it builds the customized QEMU (arm-softmmu, TCG, no display backends), bundles CPython 3.12 with Pillow/littlefs, compiles the YAFFS/UnQLite tools and runs them through one firmware-free round trip (seed database, flash image, read back, edit, read again after a cold remount), verifies every ELF's dynamic links, and packages the result together with the host runtime. The desktop app is part of the deliverable: with `linux/` present and no dotnet SDK on the host the build fails, so set `AZKI_SKIP_APP=1` deliberately when an engine-only package is wanted. Use `./scripts/build-linux.sh release` for Release.

Standalone engine build: `python3 -B scripts/build-engine.py`, emitting `dist/Engine` and `dist/Engine-sources.tar.gz`. `build/` is a reusable cache; `dist/` holds only final artifacts; one-off staging happens outside the repository and is cleaned up, exactly as on macOS.

### Downloads and indexes

Upstream tarballs and PyPI sdists are fetched from the canonical host first and from public mirrors afterwards, always verified against the SHA-256 published in the PyPI metadata, so a mirror can never substitute an artifact. Building a wheel also makes the PEP 517 backend install its own build requirements (Cython, meson-python, …); that index is pinned to `https://pypi.org/simple` instead of inheriting the host `pip.conf`, because a dead mirror there only surfaces as `from versions: none`. On a throttled link, point it at a reachable index explicitly:

```sh
AZKI_PIP_INDEX_URL=https://mirrors.cloud.tencent.com/pypi/simple ./scripts/build-linux.sh
```

Replacing the index changes who supplies the build-time toolchain; the runtime dependency closure is still checked file by file against its SHA-256.

The desktop app (`linux/`) reads file metadata through glibc's x86_64 `struct stat` layout; other hosts fail with an explicit error instead of guessing field offsets.

Faults that escape a desktop command are appended to `~/.local/share/AzkiSimulator/com.azki.AzkiSimulator/logs/gui.log` (the prefix moves with `AZKI_DATA_ROOT`); the window only shows a one-line status, so read this file when diagnosing.

Other host-side desktop paths: the connection timeout persists in `~/.config/azki-simulator/settings.json` under the key `simulator.connectionTimeoutSeconds` — the same key name as the macOS UserDefaults, default 30 and range 1–300, prefix moving with `AZKI_CONFIG_ROOT` — and it bounds only guest/external connection waits, applying from the next operation. Recordings are published to `~/Videos/Azki Simulator` (falling back to `~/Pictures/Azki Simulator`), encoded by the system `ffmpeg`; when ffmpeg is missing the record button reports that instead of degrading silently. The device window's data panel matches the macOS semantics: while running, "apply" changes what the emulated hardware senses immediately (`live-set`) and saves the next-boot value (`instance-settings` CLI); while stopped it only saves for the next boot. The manager window's host-status section reads, but never writes, the `azki-host-*` status-file sessions that the macOS app publishes under `/tmp` (or `AZKI_TMP_ROOT`).

## Differences from the macOS build

| Aspect | macOS | Linux |
| --- | --- | --- |
| Process isolation | `/usr/bin/sandbox-exec` (Seatbelt SBPL) | `/usr/bin/bwrap` (bubblewrap mount namespaces) |
| Binary integrity | Mach-O dependency rewrite + ad-hoc codesign | Links system libraries; `ldd`/RUNPATH closure check, per-file SHA-256 in `manifest.json` |
| Signing record | `signing.adHoc = true` | `signing.scheme = manifest-sha256` |
| GPL corresponding source | Homebrew recipes and upstream tarballs | Upstream tarballs + `DEPENDENCIES.json` (system libraries come from the build host's distribution) |
| Device screen | Native window + `frame.raw` | `frame.raw` only (no GTK/SDL compiled into QEMU; `--window` errors out) |
| Virtual Bluetooth radio | CoreBluetooth (experimental) | Not implemented; `--bluetooth reject/virtual`, BlueZ later |

bwrap and Seatbelt differ in grant granularity: files inside the bound read-only trees (bundled interpreter, prepared project) are fully readable, not only the manifest-pinned files; the writable scope stays strictly inside the session's private directory. A failed bwrap spawn is a hard failure with no unsandboxed fallback. If unprivileged user namespaces are disabled (some containers, hardened kernels), sessions cannot start; restore `kernel.unprivileged_userns_clone=1` or run in an environment that allows userns. The "no launcher, no launch" rule is pinned by `tests/test_isolation_fail_closed.py`: when the launcher path is missing (or is not a regular file) the isolation layer raises `isolation_unavailable` and produces **no argv at all**, while a host that does have bubblewrap must pass that gate and fail later on the plan's own checks. The mutation probe turns the test red the moment the guard is removed. The launcher path has a single definition in `bwrap_policy.LAUNCHER`, which both the argv and the existence check read. The two trampolines are standalone scripts (under `-I` they cannot import from the package), so each keeps its own literal, but their assertion follows the plan's "launcher ∈ {sandbox-exec, bwrap}" set instead of hardcoding one host's launcher: `tests/test_launch_trampoline.py` pins that — a launcher outside the set, and a call that did not come from the parent process, are both refused outright (the mutation probe turns the test red the moment launch.py loses the check).

## Tests

Regression without engine artifacts:

```sh
python3 -m unittest discover -s tests -p 'test_*.py'
```

Compilation tests for C device code need `gcc` (or clang) and `pkg-config glib-2.0`; they skip themselves when no compiler is present. The crypto bridge is pinned to byte contracts by known answers: `tests/test_system_crypto.py` compares the system ECDH output against an independent P-256 point implementation whose own arithmetic is validated by a published NIST key pair, and `tests/test_aes_modes.py` compares AES-CCM and AES-CTR against NIST SP 800-38C and SP 800-38A vectors. The same vectors run on macOS and on Linux, so a drift between the two hosts' crypto bridges turns that platform's CI red. `tests/test_peer_identity.py` forks a real second process over a unix socket and checks the kernel peer credential, because each end has to report the *other* process's pid, which is what pins the `SO_PEERCRED` layout. `tests/test_command_allowlists.py` requires the macOS UI, the Linux UI and the Python dispatcher to agree on the command allowlist: one verb more or fewer fails the build.

The desktop app has its own suite: `dotnet test linux/AzkiSimulator.Linux.sln` covers the frame header contract, the bwrap argv shape, the session descriptor, PMU ADC values, and the `open` flag constants with symlink rejection (a wrong octal-to-hex translation is only caught here). Write access for the one-shot CLI is computed by `Core/CliGrants.cs` from the action and its argv, copying the shape of macOS `StandaloneProcessSandbox.makeInspection`: only library mutations (import/delete/delete-all) get the whole firmware library, instance mutations (settings/reset/delete) get just `<library>/instances/<uuid>`, `prepare-bundled` gets the instance folder plus the reserved session root, and `sessions-cleanup` binds only the leftover roots under this app's own prefixes (`azki-b-`/`azki-sim-`/`azki-cmd-`) — `/tmp` inside the sandbox is a private tmpfs, so binding nothing means cleanup is a silent no-op. The instance identity of `prepare-bundled` is **optional** in the reference (with it the instance folder is granted, without it only the reserved session root), and Linux used to treat it as required, which refused a command the reference allows; it now follows the reference, while a malformed identity is still refused before anything is granted. `CliGrantTests` pins both shapes, and the mutation probe turns red the moment the identity becomes required again. A missing tree kills the command on a read-only file system (the mutation probe reports exactly `OSError: Read-only file system: instances`), an extra tree lets a command that saves one instance's settings wipe the library. `tests/test_cli_grants.py` parses both tables from their own production sources and compares them action by action, with `instance-delete` as the single documented difference (the reference switch has no such case; its own call site reports the refusal). With `AZKI_APP_ROOT` pointing at an extracted release package, `InstanceSettingsCliTests` performs a real bwrap plus bundled-Python round trip; CI excludes it by category (`--filter "Category!=Integration"`) because a container job cannot unshare a user namespace, and the test fails loudly rather than passing quietly when the package is missing. Broker records (native-broker's config.json/state.json) are published with `renameat2(RENAME_NOREPLACE)`: the sandboxed helper demands `st_nlink == 1` when it reads them, so the link-then-unlink idiom would leave a window its own 25 ms poll can fall into, and `tests/test_native_broker_wire.py` feeds the shapes parsed out of the C# publishers to the real Python validator. A desktop test also runs the handshake in both directions — the helper publishes a real launch.json that the C# reader parses, and vice versa. The C# side reads requests under the same rules as the writer: through a validated directory handle, symlinks refused, size bounded, and identical attributes before and after the read. Two further cross-language contracts, both invisible until something runs, have their own tests. `linux/tests/.../LogStreamCursorTests.cs` hands the incremental-log request the desktop app actually builds to the Python `log_stream.read_chunk`: an empty object `{}` is not "no cursor" — the helper refuses it, every poll fails, and the log panel stays empty for the whole session. The cursor advance rules (a missing file falls back to no cursor, a legacy bridge reports and stops, an out-of-range offset is refused) match macOS `SimulatorLogStream`. Package staging (`Core/PackageStaging.cs`) follows `SimulatorPackageImport`: the source must be a regular file of at most 32 MiB owned by us or root, with a single link, no group/other write bit and no symlink at any path level; `incoming` is created 0700 — and created with **mkdirat on the already validated directory handle** (the reference does exactly that in `SimulatorPackageImport.swift:48`: `mkdirat(root, "incoming", 0o700)`; the Linux port used to create it by path, which resolves the name a second time and would land elsewhere if the path had been replaced), the staged name is opened `O_CREAT|O_EXCL` at 0600, and the bytes are hashed while streaming (no whole-package buffering, no second read). Afterwards the source identity, both directory identities and the staged name's inode are re-checked, and a failed copy unlinks only its own inode, never a file somebody else moved into place. `PackageStagingTests` pins each of those properties, including the impostor rule. On the touch side, `TouchContactTracker` reproduces the four-state machine of the macOS canvas: a press outside the screen starts no contact, dragging off the screen lifts the finger, and releasing outside still lifts at the remembered point — otherwise the guest keeps a finger that never comes up. A property test drives five thousand random pointer sequences and asserts one thing: none of them ends with a press. The recording path is not assumed either: `RecordingTests` feeds 12 real rgb565le frames to ffmpeg and asserts with ffprobe that the result is h264 with `nb_frames == 12`, so frames lost inside the raw pipe turn the test red; separate cases cover a missing ffmpeg, odd geometry, concurrent stops and the 0600 result. "No process group survives the session" could only be checked through the end-to-end chain that needs real firmware; the decision now lives in `Core/ProcessGroupSurvivors.cs` (reading /proc directly instead of `Process.GetProcesses` plus getpgid, because another user's pid answers EPERM and every shared machine would report a survivor), and `ProcessGroupSurvivorTests` exercises it with a real process group: killing only the leader while a member lives must report the survivor, and an emptied group must not be reported (the mutation probe turns the test red the moment the scan always answers none). The manager's "new instance" path has a test as well (`ManagerViewModelTests`): the record is stored before it is shown, so a refused write leaves no phantom instance in the list, and the instance is still there the next time the window opens (`AZKI_DATA_ROOT` points at a scratch root and the class shares the `ProcessEnvironment` collection, so it does not run beside the other environment-mutating cases). The mutation probe turns the test red the moment "show it before storing it" comes back. It also turned up a concurrent-refresh defect: the window starts a refresh of its own and the user can start another while it runs, both see an empty list, and both insert the same instance, so the list shows it twice — observed twice while the whole suite ran. The refreshes are serialized with a semaphore now, so the check and the insert are one step. **The concurrent case does not catch the mutation that removes the serialization**: 300 stress rounds on a quiet machine hit it zero times (the window is narrow and needs a CPU preemption), so it is an invariant check, not proof of the fix — recorded here as it is.

The canvas coordinate mapping had no test, and writing one turned up a real omission. `CanvasGeometry` is the port of macOS `SimulatorCanvasGeometry`; the mapping formula (letterboxed and centred, exclusive right/bottom edges, the last pixel clamped) is now pinned by `CanvasGeometryTests`, which also reads the reference formula out of the Swift source and compares it word for word. The reference guards the **origin** for finiteness; the port only checked width and height, so a canvas whose origin is NaN produced the rectangle `NaN, 0, 335.8, 400`. Every comparison against NaN is false, so the bounds check passed, and a touch at window point (10,10) was delivered to the guest as device pixel **(0, 13)** — the leftmost column — instead of being refused as the reference refuses it. A probe ran the old arithmetic rather than inferring it: .NET saturates NaN to 0, so the coordinate landed on 0, not on a negative value. The origin guard is now in place, verified against the **shipped** package: the new build refuses, the old one does not. The bridge command allowlist is likewise compared with the reference item by item (`BridgeCommandAllowlistTests` parses the permitted list out of `SimulatorSessionConnection.swift` and adds `SimulatorLiveCommands`), so one missing or extra verb turns the test red — those commands (PMU ADC, package install, the external bridge) leave no trace when refused, they only leave a slider that does nothing. `BridgeInputGuardTests` pins the gate in front of them: an out-of-range touch coordinate is refused before the socket is touched (`触摸坐标超出设备画面`), an unauthorised command is refused before a connection is made (`不受支持的会话命令`), and a session directory that is not ours or is writable by others fails construction. Two more platform branches in the shared runtime now have tests: `quarantine` must be a **no-op** off macOS (content, mtime and mode unchanged), and `--window` on Linux must fail outright and point at the host control panel instead of opening a second renderer — both in `tests/test_platform_branches.py`.

Session cleanup needs one more step on Linux than on macOS: bwrap grants access by binding directories, so a stale session root inside the sandbox is a **mount point**, and a mount point can never be rmdir'd — a real run reports exactly `remove-failed: Device or resource busy`. Making `/tmp` itself writable would allow the removal, but it would also let the command unlink any entry this user owns there, which is far broader than the reference's name-prefix grant, so it is not done. The split is: the sandboxed Python applies the original rules (process and socket liveness, a ten minute grace window, an unsettled instance transaction, never touching other names, never following a symlink) and empties the tree, then the host-side `Core/SessionCleanup.cs` performs the last rmdir only for paths the receipt itself named as `remove-failed`, that were in the grant list, and that are genuinely empty — which keeps a just-created, still-empty session being prepared out of reach. The rules themselves are pinned by `tests/test_sessions_cleanup.py`, which forks a real process for its liveness evidence and builds real trees; `SessionCleanupCliTests` then runs the whole chain through the packaged CLI with real bwrap, and `SessionCleanupTests` checks each host-side refusal. The mutation probes are reported as they turned out: removing the receipt-verdict, grant-list, name-prefix, node-type or parent-directory guard is caught, while removing the emptiness check is not — `Directory.Delete` already refuses a non-empty directory, so that guard expresses intent rather than carrying safety.

Deleting an instance's data runs into the same trap: the command removes the instance directory *itself*, and a directory bwrap binds is a mount point — unlinking it is EBUSY, and while the parent arrives read-only even rmdir is EROFS (both checked against a real bwrap). The reference grants this command **nothing**: macOS's `makeInspection` has no `instance-delete` branch, so the Swift call site only reports that the helper refused the command and the instance's data stays where it is. Linux grants the `instances/` container instead and re-binds every sibling instance read-only *after* the writable bind: the same "a mount point cannot be removed" property now guards the wider grant. `CliGrantTests` pins the grant shape and the bind order, `tests/test_cli_grants.py` records that this is still a difference from the reference (Linux adds `instances`), and `InstanceDeleteCliTests` runs the whole chain through a real bwrap and checks that a sibling instance cannot be touched. The mutation probes turn all five of these red: dropping the sibling re-bind, granting the instance folder instead of the container, protecting the target as well, emitting the read-only re-bind before the writable bind, and not emitting it at all.

The command has a second trap, and it is about order: the sandboxed payload inherits the stdout/stderr pipes, and .NET closes them when the process object goes away, so waiting for the exit before reading the pipes can close them while the payload is still writing, and the payload is killed with it. `Core/InspectionRunner.cs` therefore drains both pipes before waiting for the exit, which is also the order .NET documents for redirected output, and the hard deadline still covers both waits. When memory is tight — another build on this machine has already had the kernel kill soong_build twice in a global OOM — the sandbox can be killed by a signal as a whole: the receipt is the contract, and a receipt means the command finished its work; without one, the error says which signal ended it.

End-to-end acceptance is written as one chain that is not allowed to shrink later, `FirmwareBootTests` (`Category=Integration`): import → take only a profile the catalog really reports as `availability.ready` → prepare → start → the frame sequence must advance (`FrameReader` skips the sequence it already handed out, so the second frame is a genuine repaint) → press and lift at the centre of the panel → the incremental log cursor is accepted and can be continued → the screenshot is checked for the PNG magic, its sha256 and its dimensions → `stop`, after which only qemu-system-arm processes **this test started** may remain (a session somebody else is running is not counted as a leak). The repository ships no firmware, so the test fails loudly unless both environment variables are set:

```sh
AZKI_APP_ROOT=/path/to/azki-simulator AZKI_FIRMWARE=/path/to/ota.zip \
  dotnet test linux/AzkiSimulator.Linux.sln --filter "Category=Integration"
```

The same chain also has an entry point, `scripts/verify-linux-boot.sh`: it copies none of the acceptance logic and only establishes the contract around it — the extracted package has its structure (bundled interpreter, manifest, app assembly), the firmware exists, `bwrap` is on the PATH and really starts (when it does not, the kernel has probably turned unprivileged user namespaces off, and that is an environment problem rather than a firmware problem) — then it runs the command above and checks once more, in the shell, that no qemu-system-arm **this run started** is left behind. Checked with a non-firmware file pretending to be an OTA, the script fails at the import step as expected, exits 1, and the other four integration cases pass:

```sh
AZKI_FIRMWARE=/path/to/ota.zip scripts/verify-linux-boot.sh /path/to/azki-simulator
```

When an OTA matches several models, the CLI leaves the choice in `needsSelection` instead of handing back a profile; the chain then reports the candidate IDs rather than a mystery. No authorized firmware sample exists on this machine, so **a real firmware boot has never passed here**. What is proven is the first half of the path: feeding a non-firmware file shows the command travelling through bwrap, the bundled interpreter and the allowlist into the real Python catalog validator, which answers verbatim with "import a complete OTA firmware package". The second half — frames, touch, screenshots — has since been walked with a **synthetic bootable guest** (below), and that half proves the host side, never the behaviour of real firmware.

The first step of the ladder, the import, is the only one that can be verified without the real firmware: the probe inventories structure and never judges authenticity, so a synthetic OTA has the same shape as a real one. `tests/test_firmware_import.py` (ten cases) pins the import contract — a complete ZIP or BES envelope is recognised, the unique `vela_ap.bin` is extracted into a private library object, the models the AP declares decide which presets the firmware is visible under, and anything that is not a complete OTA is refused with a reason; `FirmwareImportCliTests` then runs the same path through a real bwrap and the packaged CLI (import → an `availability.ready` entry in the listing → delete leaves the library empty).

Writing those two tests turned up a real defect: when the AP names a device the bundled catalog does not have (`miwear.watch.q66nfc` is one such name — the runtime's own Q66 profile uses it while the catalog writes `q66`), the candidates fall back to all seventeen presets but the **items stay empty**. The receipt contradicts itself, the macOS decoder refuses the whole import with "the import result has no unambiguous firmware model", and on Linux the import succeeds while the listing stays empty. `firmware_catalog.py` now lets the items follow the candidates (a declaration that matches no preset falls back like an AP that declares nothing), so the receipt always satisfies the contract it states. The change is in the shared runtime, so both platforms gain; it moves exactly one semantic. The control experiment: against the package built before the fix the import integration case reports "the receipt's candidates have no matching items"; with the fixed runtime back in the same package it passes. The next step, the preparation, also passes with a synthetic firmware: the synthetic AP is built in the shape the probe reads (chip line, partition offsets, reset sequence and a stack pointer inside the modelled RAM), so it is structurally valid but **not firmware**. What stops it is the instance storage step, which reads the NAND partition table out of the firmware and cannot find one in a synthetic image — a preparation that carries an instance identity therefore fails here with `Original NAND data partition was not found`, while the preparation *without* an identity (the one the reference allows) runs through a real bwrap: the engine is materialized, the recipe is written, and the session description and backend plan appear (`FirmwareImportCliTests`, second case). What was still missing was a payload that can actually run inside the emulator.

`linux/tests/…/SyntheticGuest.cs` is that payload: 230 bytes of Cortex-M33 Thumb-2 machine code taken from an llvm-mc listing of ARMv8-M Mainline source, touching only addresses read out of the emulator (GPIO0/1/2 = 0x40081000/0x40089000/0x4008a000, LCDC = 0x40200000, PL011 UART0 = 0x4000b000, a framebuffer at 0x20010000 in SRAM). It powers and selects the panel, programs the LCDC geometry (0x104/0x108/0x118 dimensions, 0xfc pitch, 0xf4 address, 0x100 origin, 0x210 bit29 generator, 0x264 format) and then loops: paint one 212×520 RGB565 frame, clear status bit27 (0x1c4), start the transfer (0x224 = 1), wait for 0x224 to fall and bit27 to rise, and emit one UART byte per frame. Around it the OTA carries the build_info lines the probe parses and 116-byte MTD partition records, which makes a complete package of `vela_ap.bin` + `vela_resource.bin` (with the `-rom1fs-` magic) + `version.ini`. That partition table is not arbitrary: the emulator's `bes_nor_layout_init` accepts only the eight exact geometries in its catalog (flash, ap, tail, factory and config must each match), so the synthetic `OTA_CODE_OFFSET` plus the mode/facmode/nv records have to add up to the Q66 row (ap 0xc0000, tail 0xfb8000, factory 0xfc0000, contiguous and ending exactly at the flash boundary) or QEMU exits with `NOR writeback requires an exact catalog geometry…`. The ladder itself now lives in one place, `BootLadder.cs`, so the authorized-firmware test and the synthetic one cannot drift or shrink separately (`SyntheticGuestBootTests` runs the same chain).

Before that chain passed, the Linux desktop had **never actually started a session**, and starting one turned up seven defects that only exist once something runs. Each has a regression test:

- The sandbox could not see the supervisor script. The guest bound Engine, the project and the firmware library, but never `Runtime/azki_simulator/minative_launch.py`, which its own argv names, so the interpreter reported `can't open file …` (ENOENT). That one **file** is now bound read-only, matching the reference, which treats the supervisor as a pinned file rather than granting the whole Runtime tree; a real bwrap run confirmed it creates the missing parent directories for a single-file bind.
- `SO_PEERCRED` is 17 on Linux, not the 16 a BSD `LOCAL_PEERCRED` suggests: 16 is `SO_BSDCOMPAT`, which **succeeds** and hands back four zero bytes, so the credential check failed without ever reporting an error (`PeerCredentialTests` asserts pid and uid over a real socket pair; restoring 16 turns it red with `SO_PEERCRED unavailable: 0`).
- `DataLocations.EnsurePrivateDirectory` tightened only the level it was asked for, leaving every ancestor it created at the umask default 0755 (`PrivateDirectoryTests`, three cases: the created chain, an existing owned directory, and not touching ancestors that were already there).
- Neither the helper's nor the guest's sandbox bound the private firmware library, and `start` revalidates every path the plan pins — an imported package's AP and OTA objects live in exactly that tree, so the session died on the first command.
- **bwrap forks instead of execing**, which moves two identity relationships. First, the supervisor asserted `os.getppid() != parent`, but the guest's direct parent is bwrap, so every launch was refused with `Invalid native parent`; `minative_launch.native_parent_is` is now platform-aware — the direct parent on macOS, and on Linux a launcher that really is bwrap whose `PPid` is still the announced pid. The same test doubles as the liveness check (when the host dies the launcher is reparented and the equality stops holding). `tests/test_platform_branches.py` runs the check inside a real bwrap sandbox: announcing itself reads as owner, announcing somebody else's pid as stranger. Second, the session's process group belongs to the supervisor (`--new-session` calls setsid in bwrap's child before the exec, so a `setsid()` inside the payload answers EPERM), while the pid .NET holds is **bwrap**'s — so the published pid, the `killpg` target and the "no survivors" verdict were all aimed at bwrap's group, which is empty. Measured: SIGTERM to bwrap reaps the supervisor with SIGKILL through `--die-with-parent`, skipping its bounded graceful stop and its storage receipt, and leaves the grandchild (where QEMU lives) alive in a dead group. `ProcessGroupSurvivors.GroupLeadingChild` now takes bwrap's single self-group-leading child (observed at t+29 ms and stable after; more than one is refused), and the published pid, the TERM/KILL targets and the `cleanup` verdict all follow it. `PublishTerminal` also matches the reference in keying exited/failed off whether the group was reaped, with the payload's own status travelling as `exitCode` (measured: bwrap exits 0→0 and 3→3). `ProcessGroupSurvivorTests` pins the three pictures with real process groups: a self-group-leading child is found, a child that merely inherited the launcher's group is never mistaken for one, and two group leaders are refused.
- The session logs were created with the umask default 0644, and the helper inspects run output for exactly that rule, so the session ended after its first command (`Run output must remain private and free of symbolic links`). Both logs are now created `O_CREAT|O_EXCL` at 0600, the same mode the reference opens them with.
- The guest argv was missing the virtual-peer and instance-settings argument groups. When the plan enables the synthetic peer the runner's identity carries no `virtual_peer_state_sha256` and the helper refuses with `Runner identity differs`; `--instance-settings` likewise, while `--skip-oobe` was hardcoded and is now read back from the plan's `skipOOBE`. The supervisor validates the argv shape itself (length only in 8/16/20/21/26/27, and the three instance files must be exactly the session's private paths), so a missing argument fails the launch loudly instead of degrading.
- An early failure masked its own cause: when the broker raised before it had read launch.json, the terminal record carried an empty `id`, the helper read that as "Native status does not match this launch" and the real reason was replaced by a fixed sentence. The record now uses the session identity this app sealed into config.json (the reference publishes `launch.configuration.id` too), and launch.json is validated like stop.json — the announced id must equal the sealed configuration id, and the field set must be exactly `id/run/version`.

`tests/test_native_broker_wire.py` parses every record the C# publishes and feeds it to the real Python validator; its witness table follows the renamed identifiers (`_sessionId`, `_guestGroup`), which makes it the gate on those record shapes. The CI guard that requires every bwrap-starting test to carry the Integration category used to look at files one by one and went red when the ladder moved into a shared helper: `BootLadder.cs` constructs the sandboxed runner but declares no test method, while both of its callers do carry the trait. The guard now follows callers — a file without test methods is covered by whoever names it — so a chain that starts a sandbox cannot dodge the container job's filter by moving house.

What the synthetic chain proves is the host side: real bwrap, the real supervisor script, the runner deriving board geometry from the AP, the frame file the helper mirrors, the bridge, the screenshot, and a stop that leaves no emulator behind. It proves **nothing** about real firmware; that evidence still belongs to `FirmwareBootTests`, and this machine holds no authorized bytes. Two consecutive runs against an extracted release package passed (6 s and 5 s), and a side probe captured the products independently: `<session>/frame.raw` is 220512 bytes = 32-byte header + 212×520×2, sequence 46 (even, so a stable write), 55089 distinct colours across 110240 pixels, and the screenshot's IHDR is 212×520.

## GitHub Actions

`.github/workflows/build-linux.yml` builds the engine and the Linux package inside an Arch Linux container and runs the same Python tests. Containers cannot use bwrap, so the full boot acceptance is handed to the `boot` job on a self-hosted runner: it only accepts a self-hosted machine labelled `azki-boot`, it runs only when the repository variable `AZKI_BOOT_RUNNER=true` is set and the workflow is dispatched by hand, and the firmware never travels through the workflow — the secret `AZKI_FIRMWARE_PATH` only names the authorized OTA that the machine already holds. The release pattern matches the macOS workflow: draft release, build number as “starting point + run number − 1”, checksums attached, and only `contents: write` permission. The number is written back into the `BUILD_NUMBER` file before packaging, so the package name (`Azki-Simulator-<version>-build<number>-release-linux-<arch>.tar.gz`) and the release tag (`v<version>-build<number>`) name the same build. The container job runs `dotnet test` with `Category!=Integration` to skip the cases that need bwrap, and `tests/test_ci_workflow.py` guards those conventions.
